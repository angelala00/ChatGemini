## 1. 背景与动机

两个动机：

1. **为子系统提供统一对接的 RBAC 能力**。平台内的子系统（assistant-web、developer-portal、smart office 及后续接入者）目前各自处理权限或借用 bff 的功能级权限码，缺一个可共享的授权层。需要实现一套统一的 RBAC，作为所有子系统对接权限的标准入口，子系统不再各自发明权限逻辑。
2. **借建设之机收敛项目内散乱的授权逻辑**。当前项目里的权限模型缺乏统一设计与规划，同类问题（"谁能用某功能"）由功能权限码、特性可见性、环境变量白名单三套机制并行求解（见 §2）。本次建设把其中的用户授权语义收敛到统一模型，Feature Flag 继续负责功能启用和发布控制：前期不强制迁移、后续渐进迁移，但**新的统一模型必须兼容当前项目里已有的权限能力**（能表达现有权限码、用户直挂、名单式可见性），保证存量迁移路径存在。

由此带来的直接问题（收敛的必要性）：

- **同类问题多处求解**：一个功能"谁能用"，可能由 `admin_user_permissions` 表、feature flag 的 `visible_users`、环境变量白名单三处共同决定，排查"某用户为何能看到/看不到某功能"要查三处。
- **无角色抽象**：权限直接挂在用户键上，每接入一个新用户要手工点 5~6 个权限码；同类型用户（如"平台运维"）没有可复用的授权单元。

## 2. 当前状态（2026-08，事实基准）

三套并行机制一览：

| 机制 | 控制什么 | 配置载体 | 失效回退 |

| 特性可见性 | GPTS / Library / 外部助手对谁可见 | feature flag（scope + visible_users） | env 白名单 |

### 2.1 身份与用户键

- `get_current_user`（`servers/assistant-bff/app/auth/auth_login_token.py:20`）目前为 **mock**，返回固定测试用户，字段含 `sub`/`name`/`email`/`group`（LDAP DN）/`auth_provider`。
- 权限判断使用的用户键是 **email 与 sub 双键**：`user_keys()`（`servers/assistant-bff/app/admin/access_control.py:42`）返回 `[email, sub]`，任一命中即生效。真实 SSO 落地后两者是否稳定一致，尚无验证。

### 2.2 功能权限码（用户 → 权限直接映射）

- 存储：`admin_user_permissions` 表（`servers/assistant-bff/app/storage/business_store.py:2273`），`user_key × permission_code × enabled`，无角色层。
- 现有权限码全集（6 个）：

  | 权限码 | 保护对象 | 判断点 |
  | --- | --- | --- |
  | `admin.access` | `/api/admin/*` 全部路由 | `admin_routes.py:84` `ensure_admin_access` |
  | `gpts.manage` | GPTS 管理入口 | `gpts_routes.py:99` |
  | `models.manage` | 模型配置管理 | 种子数据（见下） |
  | `permissions.manage` | 权限管理本身 | 种子数据 |
  | `feature_flags.manage` | 特性开关管理 | 种子数据 |
  | `voice_lab.access` | 语音实验室 | `voice_lab_routes.py:11` |

- 解析逻辑：`resolve_user_permissions()`（`access_control.py:61`）= DB 启用权限 ∪ 白名单回退权限。
- 白名单回退：GPTS 白名单命中 → `admin.access` + `gpts.manage`；VOICE_LAB 白名单命中 → `voice_lab.access`（`access_control.py:51-58`）。
- 种子迁移：启动时把 env 白名单写入权限表，GPTS 白名单用户获得 5 个管理权限码（`business_store.py:1822-1853`）。

### 2.3 特性可见性（feature flag + scope + 用户列表）

- 三个特性走 `VisibilityPolicyConfig`（`access_control.py:17-39`）：GPTS、Library、ExternalAssistant。
- 每个特性由三要素控制：总开关（feature flag）、可见范围 scope（all / restricted）、restricted 时的 `visible_users` 名单；无 DB 配置时回退到 env 白名单。
- 另有资源级可见性：`admin_model_configs` 表自带 `visibility_scope` / `visibility_users` 字段（`business_store.py:2243`），即模型这个资源有自己的可见性，与上面 2.3 的特性级可见性是两层。

### 2.4 环境变量白名单（第三套）

- `GPTS_WHITE_LIST` / `VOICE_LAB_WHITE_LIST` / `EXTERNAL_ASSISTANT_WHITE_LIST`（`servers/assistant-bff/app/base_config/model_config.py:93-102`），既是 2.2 的回退权限来源，又是 2.3 的回退名单来源。

### 2.5 管理界面与审计

- 前端权限管理 UI 在 `apps/assistant-web/src/views/AdminConfig.tsx`（增删用户权限码）。
- 管理操作全量写 `admin_audit_logs`，resource_key 形如 `user_key::permission_code`。

### 2.6 子系统对接现状

- 其他子系统目前仅通过 `/api/auth/userinfo` 拿身份（见 `docs/auth/bff-auth-integration.md`），**没有**任何权限查询接口；developer-portal 等的授权各自处理。

## 3. policy-agent 权限需求

> 本章记录 policy-agent 对统一权限能力的初步需求；当前先固化已确认的角色与控制对象，具体权限码和数据范围后续讨论。

### 3.1 用户角色与前端功能

policy-agent 初步需要三类角色：

1. **只读用户**：可以查看总览、使用制度问答，并使用只读检索等问答能力；不具备制度维护及其他写操作权限。
2. **制度管理员**：一般由各部门负责人及其指定的制度管理人员担任，每个部门可有一至多名制度管理员；具体可管理的数据范围待确认。
3. **业务超级管理员**：可以访问全部业务功能，包括尚未开发的预警模块；可以为指定用户分配管理员角色，具体可分配的角色及部门范围待确认。

前端应根据当前用户的授权结果控制菜单、页面和操作入口的可见性，但前端控制仅用于界面呈现，不能替代后端授权校验。

### 3.2 后端工具与技能权限

- 制度问答涉及的工具和技能需要纳入权限控制，并与用户角色对应。
- 只读用户只能调用查询、检索、读取类工具和技能。
- 获得相应管理权限的用户可以调用创建、修改等写操作工具和技能；具体能力清单后续按工具和技能逐项确认。

### 3.3 后端接口权限

- policy-agent 的后端接口需要按统一权限模型执行授权校验，不能仅依赖前端菜单或按钮控制。
- 接口权限应与前端功能、工具和技能使用同一套角色与权限语义，避免同一业务能力在不同入口出现授权结果不一致。
- 具体接口与所需权限的对应关系，后续通过接口权限矩阵补充。

### 3.4 初步授权模型

policy-agent 采用带固定业务范围的 RBAC：

```
用户(sub) ──绑定──> 应用内角色(role + scope) ──包含──> 权限码(permission)
                              │
                              └─ scope: global / department:<department_id>
```

- **只读用户**使用全局只读权限，能够查看总览、使用制度问答和只读检索能力。
- **制度管理员**在指定部门范围内获得制度管理及相应写操作权限；执行接口、工具或技能时，除校验权限码外，还必须校验目标数据是否属于授权部门。
- **业务超级管理员**在 policy-agent 应用内拥有全局业务权限，并可分配允许其授予的管理员角色；角色授予范围和超级管理员之间的授权规则仍需单独确认。
- 部门范围是 policy-agent 当前明确需要的固定授权维度，不扩展为支持任意属性条件表达式的通用 ABAC。

### 3.5 权限执行原则

- 权限码必须带应用边界（如通过 `app_id=policy-agent` 与应用内权限码组合表达），避免不同子系统的同名角色或权限相互影响。
- 前端菜单、页面和操作入口只消费授权结果用于界面呈现；后端接口是实际安全边界。
- 工具和技能需要声明其所需权限。只读工具使用读取类权限，创建、修改等写工具使用对应写权限；工具执行前必须再次校验，不能沿用未经验证的前端状态。
- 同一项业务能力在前端、接口、工具和技能入口复用同一权限语义，不分别建立平行的角色规则。
- Feature Flag 只控制功能是否启用，RBAC 控制用户是否获准使用；功能实际可用需同时满足“功能已启用”和“用户已授权”。
- 首期由 policy-agent 后端携带当前用户身份，实时调用 assistant-bff 的授权接口完成判断；暂不把权限声明写入 JWT。授权服务不可用时，受保护的写接口和写工具拒绝执行。

## 5. 目标与非目标（草案，待确认）

**目标**

1. 用户 → 应用内角色绑定（含固定业务范围）→ 权限 三层模型，角色是授权的主要操作单元。
2. 统一功能权限码、名单式可见性和白名单中的用户授权语义，同时保留 Feature Flag 的功能启用与发布控制职责。
3. assistant-bff 作为统一授权能力提供方，子应用后端通过统一接口获得授权判断结果。
4. 管理界面支持角色 CRUD 与用户-角色分配，保持审计。
5. **兼容现状**：统一模型能表达现有 6 个权限码、用户直挂权限与名单式可见性；存量数据不强制迁移，但迁移路径必须存在（呼应动机 2）。
6. 同一业务能力在前端、后端接口、工具和技能入口使用一致的权限语义。

**非目标（草案，待确认）**

- 不做通用 ABAC/策略引擎（任意属性条件表达式）；允许子应用使用已明确的固定业务范围，如 policy-agent 的部门范围。
- 不做多租户隔离。
- 不替换认证（SSO/session 归 `docs/auth/`，本域只管授权）。
- 前期不迁移存量权限数据（只做能力兼容设计，迁移另行排期）。

## 6. 概念模型草案（strawman，欢迎推翻）

```
用户(sub) ──分配──> 应用内角色绑定(app + role + scope) ──包含──> 权限码(permission)
                                       │
可选直通: 用户也可在应用边界内直接挂权限码（兼容现状 admin_user_permissions）
```

- **应用**：角色、权限码和授权关系均需有明确的应用边界；同名角色不能天然跨应用继承权限。
- **角色**：内置角色（如 `platform-admin`、`feature-operator`）+ 自定义角色两类；角色与权限码多对多。
- **角色绑定范围**：角色分配可携带少量、预先定义的业务范围。无范围需求时使用 `global`；policy-agent 制度管理员使用部门范围。
- **权限码**：应用边界内沿用 `domain.action` 命名，新增 `roles.manage`；policy-agent 的具体权限码在接口、工具和技能清单完成后确定。
- **功能开关与授权**：feature flag 保留总开关和发布控制职责，RBAC 负责用户授权；两者共同决定功能是否可用。现有 `visible_users` 的迁移方式另行确定。
- **执行边界**：子应用后端、工具执行器和技能执行入口都必须执行授权校验；前端权限只用于展示。
- **迁移**：现有 `admin_user_permissions` 原样保留为"用户直挂权限"，白名单 seed 逻辑冻结只读。

## 8. 决策记录

- **2026-09-01｜跨应用授权形态**：首期由子应用后端携带当前用户身份，实时调用 assistant-bff 的授权接口；前端只消费授权结果用于展示，暂不使用 JWT 权限声明。
- **2026-09-01｜应用隔离**：角色、权限码和授权关系必须具备应用边界，避免跨子系统的同名角色或权限相互影响。
- **2026-09-01｜固定业务范围**：角色绑定允许携带子应用明确需要的固定范围；policy-agent 制度管理员使用部门范围，但不建设通用 ABAC 表达式引擎。
- **2026-09-01｜统一执行语义**：前端、后端接口、工具和技能使用同一权限语义；后端及工具/技能执行入口负责实际授权校验。
- **2026-09-01｜Feature Flag 边界**：Feature Flag 负责功能启用和发布控制，RBAC 负责用户授权；功能实际可用需同时满足两者。现有名单式可见性如何迁移仍待确认。
